## Interpretation

1. **The link itself is not throttled.** Pinned H2D reaches 25 GB/s, the practical ceiling of PCIe 4.0 ×16, so the vGPU did not visibly cost bandwidth in this run. Reaching it takes transfers of 1 MiB or more: a single 64 KiB copy gets only 4.5 GB/s.
2. **A naive miss fetch is bound by the number of copies, not bytes.** One copy per page costs ~8.5 µs whether it moves 4 KiB or 64 KiB. The best PyTorch-level page fetch reaches 7.7 GB/s, 30% of the link. Staging through a CPU gather is worse for pages (5.1 GB/s), but 27× better than per-copy for 4 KiB tokens (11.6 GB/s at 512 tokens). Token-level fetching is therefore viable only when batched, and reaching link speed for pages needs a GPU-side gather from pinned memory (what HiSparse's fused kernel does) or a multithreaded, pipelined gather. That is prototype work, not sprint work. Whether mapped pinned memory works on this vGPU is untested.
3. **The dense baseline fits but is pessimistic.** *Hypothesis:* HF eager decode is CPU-launch-bound at ~31 ms up to 16K, and GPU work only exceeds launch time at 32K. The 16K → 32K increase (+11.5 ms) is about 3× the cost of reading the extra KV once (~3.4 ms at 696 GB/s), so this code path likely moves the KV more than once per step (`DynamicCache` appends with `torch.cat`, copying the cache each step). A later HiSparse-vs-full-KV throughput comparison needs a fairer baseline (static cache, CUDA graphs).
4. **Trace collection is cheap.** 1,000 decode steps at 32K take ~45 s plus selector overhead, and a 10K-token reasoning trace takes ~5–6 min. Longer Workload B traces are affordable.
5. **First estimate for open question Q5** (*assumption:* 10% miss rate, k = 128 pages, 36 layers). Misses move ~461 pages ≈ 29 MiB per request per step: 1.2 ms at link speed, 3.9 ms with the per-page loop. Against the ~31 ms HF-eager step, that is 4–13% at batch 1. Miss time would match the step time around batch 8 (loop) to 26 (link speed), and sooner with a faster decode engine.

Caveats: a single run. Load from another VM on the same A40 is invisible from inside this VM, so `bandwidth.py` should be re-run once at another time before these numbers are quoted. The PCIe generation and width are hidden. It is unknown whether the CPU-heavy experiment in the `run` session overlapped with this run, which would affect the `stage` rows.
